## Problem
`scripts/contracts.py` already has `check_stage0_fit_gate()`, `check_draft_manifest()`, `check_verification_receipt()`, and `check_freshness()` — correct, already-used-for-reporting primitives — but a grep across `scripts/*.py` confirms only `check_finalize_ready()` (Stage 3) is ever called as an *enforced blocking* precondition, inside `finalize_submission_job.py`'s `_require_ready` (with a visible, explicit `--force` override). The Stage 0/1/2 equivalents are imported only by `scripts/check_submission_status.py`, for read-only reporting — never as a gate inside the scripts that actually produce each stage's artifacts (`scripts/build_authoring_packet.py`, `scripts/author_from_packet.py`). A stage can be silently skipped, or re-read stale, and nothing stops it from being reported done except at Stage 3, and only if Stage 3 is actually attempted.

Live evidence on disk right now, not hypothetical: three submissions (camunda, ncontracts, paylocity under `data/submissions/`) have a `verification_receipt.json` generated **before** the current `Resume.md`/`CoverLetter.md` were last edited — stale by mtime, which is also fragile to clock skew, `touch`, and checkout operations, the only freshness signal that exists today. Separately, zero submissions touched in the batch that surfaced this problem have a populated `draft_manifest.json`/rubric score, and nothing today forces that to exist before a submission could be reported done.

## Decision
Extend the existing Stage-3-gate pattern to Stages 0-2 rather than inventing new tooling — the primitives already exist, tested, and unused as gates:

1. Add two new `contracts.py` functions, `check_stage1_ready()` and `check_stage2_ready()`, matching `check_finalize_ready()`'s exact return shape (`tuple[bool, list[str]]`), built from the existing `check_stage0_fit_gate` / `check_draft_manifest` / `check_verification_receipt` / `check_freshness` / `load_json` primitives.
2. Wire these as blocking preconditions inside the producing scripts, force-overridable exactly the way `finalize_submission_job.py` already is (explicit `--force` flag, never a silent skip — see item 5 below for how Stage 2's override differs):
   - `build_authoring_packet.py` calls `check_stage0_fit_gate()` before building a packet (Stage 0 exit / Stage 1 entry).
   - `author_from_packet.py` calls the new `check_stage1_ready()` (packet `packet_status == "ready"` + both `Resume.md`/`CoverLetter.md` present) before compose (Stage 1 exit / Stage 2 entry). **The `packet_status == "ready"` condition has no `--force` override, at all** — see item 5.
   - `author_from_packet.py --verify-only` and `verify_submission.py` call the new `check_stage2_ready()` (fresh verification receipt + `draft_manifest.json` with a populated `rubric_score` + zero linter `HARD_BLOCK`s + `--audit` run whenever a rubric score is present + `claim_provenance.py` run with its findings surfaced as a WARN-tier field, see item 7) before Stage 2 can be reported complete.
3. Replace mtime-only freshness with a stored content hash: `verification_receipt.json` gets a `content_hashes` field (sha256 of `Resume.md`/`CoverLetter.md` at verify time); `check_freshness()` compares current file hashes against the stored ones. Keep mtime as a cheap pre-check, not the sole signal.
4. `verify_submission.py --audit` becomes a required call inside `check_stage2_ready()` — not an optional extra command — before `draft_manifest.json`'s `verification_passed` can be set `true`. Reopening the byte-identical-rubric-score failure mode this was built to catch (8 submissions once got identical, non-real sub-scores presented as genuine) is treated as a regression, not an edge case.
5. **`--force` policy — three tiers, not two.** Every `--force` override, at every stage gate that has one, gets appended to a persistent log file at the point of use — today "visible" only means visible in the terminal that ran it, which is not durably recorded.
   - **Stages 0 and 3 keep the existing bare-flag `--force` semantics, unchanged.** Both gate on process/staleness conditions (a missing/invalid `stage0_fit_gate.json`; a stale or failing finalize precondition) with real, legitimate override cases already documented in code (e.g. `finalize_submission_job.py`'s own docstring: "correcting an already-verified row's title/casing").
   - **Stage 1's `check_stage1_ready()` has NO override for its `packet_status == "ready"` condition — not even with `--force`.** This is a content-safety gate, not a process gate: `packet_status: incomplete` means one of CR-074's five fail-closed conditions fired (unmapped required item, disabled claim, missing excerpt, Skip tier, over budget), and forcing past it permits authoring from a packet with no evidence for something the JD requires. There is no legitimate override case for that, unlike Stage 0/3's bare-`--force` cases. This matches the existing, deliberate behavior in `scripts/test_author_from_packet.py`'s `test_non_ready_overrides_force` ("force does not bypass packet_status check — only the version check") — this CR keeps that behavior rather than loosening it. The only way past an incomplete packet is fixing Stage 0 / the packet itself.
   - **Stage 2 requires `--force` *and* a non-empty `--force-reason "..."` string.** Once `check_stage2_ready()` requires `--audit` to run clean before a rubric score counts, `--force` at Stage 2 becomes the only way past a real `--audit` duplicate-score flag — the exact decision point the byte-identical-rubric-score incident lives at (that incident wasn't caused by someone bypassing a gate with `--force`; it was fabricated data passing a superficial check, which is precisely what `--audit` now exists to catch). A bare `--force` with no reason is rejected at Stage 2 only.
6. **`.claude/workflows/generate-submission-batch.js` — patched, not deprecated.** Re-reading the file itself (not a secondhand description) shows it is a deliberate, already-justified design: its Author/Review split and Cross-Batch Sweep phases exist specifically to fix two confirmed real defects from a prior 16-submission session, cited in the file's own header — self-anchoring cover-letter closers copied across companies, and self-graded review where the same agent drafts and scores itself. It also already contains a defensive `JSON.parse` fallback (dated 2026-08-06) for failure mode #5 from the deliberation (the Workflow tool's array-param-as-JSON-string bug). Its Finalize phase already implements the exact pattern this CR is generalizing to Stages 0-2 — it requires `check_submission_status.py` to print `STATUS: DONE` before running `finalize_submission_job.py`, gated by `contracts.check_finalize_ready`, per the script's own comment ("not just a prompt instruction anymore"). None of that is being touched. The actual defect: `authorPrompt()` (~line 131) still points every Author agent at `data/agent_context_pack.md` / full `CLAUDE.md` — the pre-CR-074 context path — never migrated to CR-074's lean `authoring_packet.json` + `authoring_rule_digest.md`. That per-agent cost (~100-150k tokens), not the 3-agents-per-company Author/Review/Finalize split itself, is what turned 12 companies into the incident. Separately, the file's own header states "still not run against a real JD yet... first real run should be treated as a dry run" — the triggering incident was its first real invocation, run unattended at full 12-company scale, past that stated caution. Two concrete fixes, both in scope here:
   - Patch `authorPrompt()` to read `authoring_packet.json` + `authoring_rule_digest.md` instead of `agent_context_pack.md`/full `CLAUDE.md`.
   - Add a structural guard inside the script that refuses to process more than ~3 companies in a single invocation without an explicit override flag — enforcing the file's own "treat the first run as a dry run" caution in code, not left as a comment nobody reads before invoking it at scale.
7. **`claim_provenance.py` — wired in this CR, WARN-only.** `check_stage2_ready()` runs `scripts/claim_provenance.py` and surfaces its findings inside `verification_receipt.json` as a WARN-tier field — same tier as today's `LW-009-PAIR`/coverage warnings. It does not block `verification_passed` or Stage 2 completion. Because a WARN nobody reads is equivalent to no check at all, implementation must also add `scripts/claim_provenance.py` to CLAUDE.md's "Required Verification Before You're Done" command list, alongside `check_ground_truth_coverage.py` and `jd_term_extractor.py` — same owner, same mechanism as those existing WARN-class checks, not a new unread JSON file. (This CLAUDE.md edit is implementation work for whoever builds this CR, not performed as part of this spec.)
8. **Scope widened: Stage 1's authoring output contract now emits `claim_provenance.json`.** Tech-lead's implementation pass found item 7 alone doesn't work: nothing today writes `claim_provenance.json`, so every receipt would report the identical `claim_provenance.json not found` forever, which both defeats the point of the WARN (nobody reads a permanently-identical message) and means the evidence the HARD_BLOCK graduation bar depends on (below) can never accumulate. Rather than deferring this to a separate CR, Jason has approved widening this CR to close the actual gap: `author_from_packet.py`'s compose-pass instructions (`_PREAMBLE`, ~line 54-69 — currently "Output exactly two fenced Markdown code blocks... Resume.md... CoverLetter.md") are amended to require a third output block, `claim_provenance.json`, in the exact schema `scripts/claim_provenance.py`'s own docstring already documents:
   ```json
   {
     "company": "...",
     "resume_claims": [{"bullet": "...", "claim_ids": ["ACC-104", "MET-10"]}],
     "cover_letter_claims": [{"proof_point": "...", "claim_ids": ["ACC-117"]}]
   }
   ```
   This is mechanically derivable by the compose agent as it writes each bullet: the packet's own `evidence_map` already ties each `jd_item`/`bucket` to specific `claim_ids`, so the agent is already choosing which packet claim to draw from for each bullet — this instruction asks it to record that choice, not do new work. `author_from_packet.py` writes the third block to `data/submissions/{slug}/claim_provenance.json` alongside `Resume.md`/`CoverLetter.md`, the same way it writes the other two today. This does touch CR-074's authoring-prompt output contract, which this CR's Metadata originally said it wouldn't — that boundary is deliberately crossed here, not accidentally.

### Deferred: `claim_provenance.py` graduation to HARD_BLOCK
Still not decided here, and still deliberately not scoped as an acceptance criterion of this CR (see Acceptance Criteria) — item 8 above only fixes *emission*, it does not change the WARN-only decision from item 7. Promoting `claim_provenance.py` from WARN to a blocking check inside `check_stage2_ready()` requires running it against a real batch (~10-15 submissions, roughly CR-074's calibration-set size) with a false-positive rate Jason has personally confirmed by reading the flagged cases himself — the same bar `--audit`'s duplicate detector cleared before it earned mandatory status (item 4 above). This is explicitly a future decision, to be made after that evidence exists, not a default outcome of this CR landing. Item 8 is what makes that evidence collectible; it does not itself decide the graduation.

## Out of Scope
- Any form of git-tracking `data/submissions/` or `data/archive/` — both are already gitignored by design (real PII in every `Resume.md` header) and `scripts/audit_public_repo.py` already hard-blocks those exact prefixes from being tracked. Ruled out; do not re-propose.
- A submission event log for tracking folder moves/deletions — its one motivating case (Veeva's folder "vanishing") was confirmed in R8 to be `scripts/archive_submission.py`'s normal apply-time move to `data/archive/submissions/`, not data loss. Not worth building for a problem that doesn't exist.
- Widening Stage 1's default context back toward `agent_context_pack.md` / full `CLAUDE.md` — CR-074's token-conscious packet path is unchanged by this CR; this work only adds enforcement around it.
- Promoting `claim_provenance.py`'s findings from WARN to `HARD_BLOCK` inside `check_stage2_ready()` — the WARN-tier wiring, and making Stage 1 actually emit the file (Decision items 7 and 8), are in scope; graduating the check to blocking is a separate, evidence-gated future decision (see the "Deferred" subsection under Decision), not something this CR does or schedules.
- Backfilling `claim_provenance.json` for the 41 existing submission folders authored before this CR lands — AC11 only requires it for newly-authored submissions; legacy folders correctly show the WARN as "not found" rather than being force-migrated.
- A regression test on `verify_submission.py`'s own exit-code-vs-printed-verdict bug (the "false PASS" bug found and fixed the same night as the triggering incident) — already fixed in code per the deliberation record; a dedicated regression test for it is worth doing but is a small, separable task, not stage-gate scope.
- Any change to `check_submission_status.py`'s DONE/INCOMPLETE computation logic — it stays the read-only status oracle; this CR makes the *producing* scripts refuse to proceed on bad upstream state, a different mechanism from status reporting.
- Harness-orchestration-layer bugs (e.g., the Workflow tool's array-parameter-as-JSON-string bug observed during the triggering incident) — a bug in the calling harness's tool-call marshalling, not something a Python-side contract change can fix. (`generate-submission-batch.js` already carries a defensive fallback for this specific bug, dated 2026-08-06 — unrelated to this CR, not being touched.)
- Deleting, relocating, or restructuring `generate-submission-batch.js`'s Author/Review/Finalize three-phase design or its Cross-Batch Sweep phase — that design is a deliberate, already-justified fix for confirmed real defects (self-anchoring cover-letter closers, self-graded review) and stays as the legitimate mechanism for the opt-in independent-review ladder. Only the two specific defects in Decision item 6 are in scope.

## Second Revision — RESOLVED 2026-08-07 (implementation-level conflicts, found during tech-lead's epics pass)

2. **OQ-2 — nothing emits `claim_provenance.json`, so item 7's WARN wiring was permanently inert as originally scoped.** Fixing this means editing CR-074's authoring-prompt output contract, which this CR's Metadata originally said it wouldn't touch. RESOLVED: Jason chose to widen this CR rather than spin off a follow-on — see Decision item 8 and AC11.
