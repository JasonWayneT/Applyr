## Problem
Two real, confirmed, live gaps — found by reading the code directly, not inferred from the architecture discussion:

1. **`server/routes/jobs/files.ts:85-108`** (`PUT /api/jobs/:id/files/:filename`, the editor-save route) gates PDF export by reading `draft_manifest.json`'s `verification_passed` field directly:
   ```ts
   if (manifest.verification_passed !== true) {
     return res.status(400).json({ error: '...' });
   }
   ```
   This is the *only* check. Unlike `scripts/finalize_submission_job.py`'s `_require_ready()`, which calls `contracts.check_finalize_ready()` — independently re-deriving pass/fail from `verification_receipt.json`'s own `mechanically_verified` flag, freshness, and rubric shape — this route trusts the manifest's boolean at face value. A hand-edited `draft_manifest.json` (or a stale one written before a real failure) flips this gate open with no independent cross-check. This is the literal, in-code instance of "agent-self-reported completion" the whole workflow-authority redesign exists to close, and it is still open today.

2. **Same route, lines 109-128**: every manual editor save that touches `Resume.md`/`CoverLetter.md` recompiles the PDF (`style_compliance_guard.py` → `compile_single.py`) with no concept of Stage 2 invalidation. If a submission was already Stage-2-complete and a human edits the resume through the UI afterward, nothing marks Stage 2 (or the eventual `workflow_state.json`) stale — the old completion status stands even though the underlying document changed. This is a write path the frozen architecture's hash-invalidation table (`Resume/CL/provenance changed → Stage1 STALE; all Stage 2 reviews; restart from Truth`) doesn't yet reach, because nothing in this route talks to the workflow layer at all.

`scripts/check_submission_status.py` was checked too and is **not** a gap of the same kind — it independently re-checks both `verification_receipt.json.mechanically_verified` (via `contracts.check_verification_receipt`) and `draft_manifest.json.verification_passed` as separate, both-required line items, so a forged manifest alone doesn't flip its DONE verdict. The gap is specifically the TS export/save path, not the Python status oracle.

## Decision
1. `server/routes/jobs/files.ts`'s PDF-export gate (`PUT /api/jobs/:id/files/:filename`) stops reading `draft_manifest.json.verification_passed` directly. It calls into the workflow authority instead — `contracts.check_workflow_complete()` (or the narrower per-stage predicate CR-077 exposes for "Stage 2 complete") via a Python subprocess call, matching the existing `runPythonScript()` pattern this file already uses for `verify_editor_save.py`/`style_compliance_guard.py`/`compile_single.py`. No new IPC mechanism — reuse what's already wired.
2. The same route's manual-save path triggers the workflow layer's hash-invalidation on write: after `Resume.md`/`CoverLetter.md` is saved and recompiled, the route calls the CR-077 invalidation hook (`scripts/workflow/invalidate.py`, once it exists) so a save after Stage 2 completion correctly demotes workflow status to `STALE` rather than leaving the old `COMPLETE` standing. Exact call shape depends on CR-077's landed API — this CR's implementation adapts to whatever CR-077 actually ships, not a pre-guessed interface.
3. `scripts/finalize_submission_job.py` and `scripts/check_submission_status.py` migrate from `contracts.check_finalize_ready()` / ad hoc manifest reads to `contracts.check_workflow_complete()` as the single completion predicate, once it exists and is proven (CR-076/077). `check_finalize_ready()` itself is not deleted — CR-075's gates stay live underneath per the frozen architecture's Principle 3 — but it stops being the *only* signal these two scripts trust.
4. No behavior change ships to the live Applyr app until `check_workflow_complete()` has been run against the real, already-on-disk submission folders (via the CR-076 adopt path) and its verdict matches what `check_submission_status.py` reports today for every folder currently DONE. A mismatch is a bug in the new predicate, not a reason to override it silently.

- Resolving the open design question from session-006 R2/R3 (whether `stage_receipts/` for Stages 0/1/3 duplicates what `contracts.py` already derives) — that's Cursor's call on their track; this CR adapts to whatever ships.
